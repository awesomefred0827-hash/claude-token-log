# Where my Claude Code tokens actually go (7 days of logs)

After three "token-saving" tools all raised my cost (see [README](README.md)), I stopped looking at tools and measured where the cost comes from.

## Method
- Source: my local Claude Code session logs (the JSONL transcripts Claude Code keeps on disk), numbers only.
- Period: 2026-09-30 to 2026-10-06, daily average. About 4,400 model calls per day.
- Cost-weighted tokens (input = 1): input 1, cache write 1.25, cache read 0.1, output 5.
- Daily average: input 9,197 · cache write 17.57M · cache read 790.05M · output 3.69M tokens = 119.42M cost-weighted.

## What I found
| Where | Share of daily cost |
|---|---|
| Cache reads (re-reading the context on every call) | 66% |
| Cache writes | 18% |
| Output | 15% |

- **Context length is the leak.** The average call carried about 184K tokens of context. Calls with more than 200K tokens of context were 1,726 per day and **56% of the cost**.
- **Every session starts heavy.** The median first call already carried about 62K tokens (292 sessions): system prompt, instructions, tool and skill lists. That block rides along on every later call.
- **Cache breaks cost 6.5%.** 75% of that came after a gap of more than 60 minutes between calls (the cache had expired, so the whole context was written again).
- **Tool output is small.** Command output about 6.8%, file reads 2.6%, search 0.3%. This is why compressing tool output did not help me.
- **Subagents.** Moving bulk work from subagents to plain scripts cut subagent cost from 63.8M to 14.0M per day (−78%).
- **My orchestration layer did not save tokens.** I run a manager session that coordinates other sessions, plus hooks. The manager uses 11.3% of daily cost, and the hooks use 0.8%. Week over week, main-session cost went up 36% while subagent cost went down 78%. The two weeks had different workloads, so this is not a clean comparison.

## Simulation: replaying my real calls with different habits
I replayed the same week of calls with three rules and recounted the cost. These are upper bounds. Starting fresh means re-reading files, so I count only **half** as the expected saving.

| Rule | Upper bound | Expected (half) |
|---|---|---|
| A. Start fresh (`/clear` + a short handover note, back to ~70K) when context passes 150K | −29.0% | about −14% |
| C. Start fresh after a gap of more than 60 minutes | −14.8% | about −7% (overlaps with A) |
| B. Trim the always-loaded context from ~62K to ~32K | −9.4% | about −5% |
| A + B + C | −42.6% | **about −21%** |

- I tried caps at 100K, 150K and 200K: −29.9%, −29.0% and −24.3%. 100K and 150K are almost the same, so 150K means less re-reading.
- I do not use auto-compact. I keep it off and use `/clear` with a handover note, because a compacted conversation can't be undone.

## Questions
- When do you `/clear`? At a token count, at a task boundary, or after a break?
- Has anyone measured how much re-reading a fresh session needs after `/clear`? That number decides whether the "half" assumption above is too optimistic.
